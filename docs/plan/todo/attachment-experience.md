# 功能計劃：附件輸入與聊天呈現

> 狀態：第一版已實作（2026-10-02）；桌面 WebView 與 Telegram 手機實機驗證待補
> 建立日期：2026-10-02
> 目標：附件在輸入框內立即佔位，送出後以縮圖／檔案卡片呈現，歷史紀錄也能正常查看。

## 1. 現況與問題

- `ChatView.js` 已有待送出附件卡片，但位於輸入框容器外，附件與當次訊息的關聯不明顯。
- `uploadFiles` 等整批上傳結束才加入卡片，上傳期間只有迴紋針的載入圖示，沒有各檔案的佔位與狀態。
- 輸入框已有一般 placeholder，但沒有隨附件狀態調整的引導文字。
- 送出時，前端將 `[附件] 絕對路徑` 加進 `data`；後端把同一字串儲存、廣播並交給 agent，使用者氣泡直接呈現完整路徑。
- 原始檔名只保存在送出前的前端狀態；伺服器以隨機檔名儲存，現有歷史文字無法還原原始檔名。
- 待送出縮圖使用本機 object URL，送出後會釋放。上傳檔目前沒有供前端使用的驗證讀取端點。
- 訊息佇列目前只儲存文字，附件資料必須同步納入排隊與重新連線流程。

## 2. 第一版體驗

### 輸入框

附件列放進與 textarea、工具列相同的外框，排列為「附件列 → 文字輸入 → 工具列」。沿用現有暗色介面與附件卡片樣式。

- 選擇、貼上或拖放檔案後立即建立卡片；圖片顯示本機縮圖，其他檔案顯示類型圖示、原始檔名與大小。
- 每張卡片有 `uploading / ready / error` 狀態。上傳中顯示載入指示，失敗時在卡片內顯示原因及「重試／移除」。
- 任一附件仍在上傳或處於失敗狀態時，按鈕與 Enter 都不可送出；失敗檔案需重試成功或移除。
- 有附件且文字空白時，placeholder 顯示「想請我如何處理這些附件？（可直接送出）」。執行中則保留排隊提示。
- 支援只有附件的訊息，以及一次多個檔案；多檔案在手機寬度下換行，長檔名截斷但可查看完整名稱。
- 切換到 Shell 模式時收起 agent 附件列，送出 Shell 指令只依文字判斷；回到 agent 模式恢復該 session 的待送出附件。

### 送出與聊天紀錄

- 使用者訊息上方顯示附件，下方顯示文字。圖片可點擊放大；其他檔案顯示原始檔名、類型及大小，提供下載。
- 主畫面只呈現使用者文字與附件卡片。完整伺服器路徑放在明確開啟的「附件詳細資訊」，不放在 placeholder、一般 tooltip 或複製訊息中。
- 附件讀取失敗或檔案已不存在時保留卡片與檔名，顯示「附件無法讀取」並可重試，不讓整則訊息消失。
- 排隊清單呈現文字摘要、附件檔名及數量，不顯示路徑；任務輪到執行後，聊天室仍保留完整附件資料。
- 文字複製沿用現有動作；含附件時可附上原始檔名，圖片預覽與下載按鈕不觸發訊息長按選單。

示意：

```text
輸入框                         送出後的訊息
┌────────────────────────┐    ┌────────────────────────┐
│ [縮圖] 畫面截圖.png  ×  │    │ [可放大的圖片縮圖]      │
│        240 KB · 已就緒   │    │ 畫面截圖.png            │
│ 幫我看一下這個畫面       │    │ 幫我看一下這個畫面       │
│ 📎                 送出 │    └────────────────────────┘
└────────────────────────┘
```

## 3. 資料與協議設計

### 附件資料

新增附件 metadata 表，至少包含：`id`、`session_id`、`original_name`、`storage_name`、經後端判定的 `mime_type`、實際 `size`、`created_at`。儲存位置由伺服器從 metadata 與 runtime workspace 解析，客戶端不能指定任意路徑。

在 `messages` 與 `queued_messages` 新增 `attachment_ids` JSON 欄位，預設 `[]`，維持使用者選擇順序。讀取訊息、sync 和 queue 時，批次解析為公開的 `attachments` 資料，避免逐則查詢。

metadata 留存與實際檔案一致：檔案寫入成功後才建立 metadata；metadata 寫入失敗時清除本次新檔案。

### API 與 WebSocket

| 介面 | 修改 |
| --- | --- |
| `POST /sessions/:id/uploads` | 回傳附件 ID、原始檔名、類型、實際大小與驗證讀取 URL；過渡期保留現有 `path/name` 回應以相容舊前端 |
| `GET /sessions/:id/uploads/:attachmentId` | 新增驗證讀取端點，支援圖片內容與下載；由 ID 查表，確認屬於該 session |
| 附件詳細資訊端點 | 使用者明確要求時才回傳伺服器完整路徑，使用相同驗證及 session 關聯檢查 |
| WS `input` | `data` 保存文字，新增 `attachment_ids`；後端驗證 ID 存在且屬於目前 session |
| WS `user_message` | 廣播已儲存的訊息 ID、時間、文字及公開附件 metadata |
| 歷史 API、WS `sync`、`queue_update` | 統一攜帶 `attachments`，前端共用映射與渲染邏輯 |

訊息與其附件 ID 必須一起完成儲存，成功後才回報接受與執行。若儲存或驗證失敗，回報可辨識的錯誤並保留輸入草稿。前端清空輸入與附件需以後端接受回應為準；加入 request ID 以對應本次送出，待確認期間禁止重複點擊。斷線未確認時保留草稿，提示確認歷史或佇列後再重試。

後端在呼叫 runner 前，將純文字及已驗證附件解析為 agent prompt，例如 `[附件] 原始檔名\n路徑：...`。聊天資料保留文字與附件結構，prompt 的組合集中在單一 helper，直接執行與排隊執行共用。只有附件時也能啟動任務；不另行改寫各家 CLI 的多模態協議。

### 驗證圖片讀取

目前 `apiFetch` 以 Bearer 或 `X-Telegram-Init-Data` header 驗證，直接使用 `<img src="API URL">` 無法帶入這些 header。

- 前端用 `apiFetch` 讀取 blob，再建立 object URL 供縮圖、燈箱及下載使用。
- 延遲載入歷史圖片，限制同時讀取數量；卸載、session 切換及失效時取消請求、釋放 URL，避免整段歷史都常駐記憶體。
- 檔案回應採私有快取設定，下載時使用安全的 `Content-Disposition` 原始檔名；文字類附件以下載呈現。
- 新附件端點沿用現有登入規則與 session 存在性驗證，不新增現有系統沒有的使用者 ownership 規則。不得透過 ID 讀取其他 session 的附件或任意檔案。
- 新端點使用現有 API base path helper，支援反向代理子路徑。

## 4. 既有資料相容

- 純文字訊息、Shell、既有 agent 與 @mention 流程維持相容；未帶附件欄位的舊客戶端仍能送出文字。
- 舊訊息若開頭包含系統產生的 `[附件] workspace/uploads/...` 絕對路徑，採嚴格識別的顯示轉換，將路徑收合為「舊附件」卡片，剩餘文字照常呈現。
- 舊資料只剩隨機檔名，不宣稱能還原原始檔名或檔案大小。第一版顯示可辨識的既有檔名與相容提示；未登錄為 metadata 的舊附件不直接提供圖片讀取。
- 相容轉換不覆寫原始歷史、不誤改使用者一般文字中的路徑，也不接受從前端提供的舊路徑作為新讀取 API 的輸入。

## 7. 範圍與後續

第一版涵蓋當次輸入的附件狀態，以及已送出／排隊附件的持久化。尚未送出的附件跨重新整理恢復、批次附件管理、跨 session 附件轉發與未引用檔案的定期清理留待後續。移除待送出卡片仍只代表不附加到本則訊息，不立即刪除伺服器檔案。

各家 CLI 是否能解讀圖片內容仍需按現有待辦實測；本次保證附件路徑正確交給 runner，不將路徑傳遞等同於模型已成功理解圖片。

## 8. 實作與驗證紀錄（2026-10-02）

- `go test ./...` 通過。新增 DB／API／WS／media 測試，涵蓋重新開啟資料庫、附件順序、跨 session 與重複 ID 拒絕、附件 metadata 寫入失敗清理、驗證讀取及中文下載檔名。
- 佇列轉為歷史訊息採同一個 transaction；歷史写入失敗或附件在排隊期間消失時，原排隊訊息保留並暫停。

- Headless Edge 使用真實前端元件、模擬 API／WebSocket：驗證輸入框內卡片、立即佔位、Enter／按鈕阻擋、動態 placeholder、接受回應前保留文字、圖片放大、歷史刷新與驗證標頭。
- 瀏覽器驗證也涵蓋上傳失敗重試、送出拒絕保留草稿、中文檔名下載、詳細資訊明確開啟後才顯示路徑、上傳中移除與切換 session 的競態、只有附件的排隊與重新整理、390 px 寬度無水平溢出，以及舊路徑格式的保守顯示／複製。
- Web Bearer 與模擬 Telegram initData 標頭均已驗證；Telegram 情境另以 `/mini` 反代子路徑執行。瀏覽器測試未呼叫真實 agent CLI，也未使用實體手機或 Wails WebView。
- 新增前端元件 `internal/static/js/chat/AttachmentCards.js`，由 `index.html` 載入；前端仍沿用 no-build 架構。
